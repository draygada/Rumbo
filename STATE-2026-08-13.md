## The root cause found on 08-13

**`canvas-ingest` was deleting every extracted document, every 6 hours.**

It upserts full rows on `(user_id, source_type, external_id)`, and every row it
builds authors a fresh `normalized_text` and `raw_payload`. For a file that text
is just the display name; that payload has no `rumbo_*` keys. LlamaParse
extraction writes the parsed document into those same two columns.

So each sync replaced ~21,000 characters of parsed lecture with a filename and
wiped the extraction markers — which made the row look never-extracted, so
nothing downstream noticed and no error was raised anywhere.

Measured: **123 of 123** successfully-parsed documents reduced to 10–39
characters, while their job rows still recorded `chars_written` averaging
21,226 and peaking at 346,573. A 100% loss rate, every course, every file type.

Two things this corrected:

- The 27 `result fetch 404` jobs looked like the problem. They are a separate,
  much smaller failure (the poller was dormant 22 days; LlamaParse had
  garbage-collected those results). Chasing them first was a dead end.
- The tidy null markers that made those 27 look cheaply retryable were the
  **fingerprint of the clobber**, not good luck.

**Fixed in `4bd3bb4`** — before each upsert chunk, load existing rows and carry
their extracted text and `rumbo_*` markers onto the fresh Canvas payload. Gated
on the markers, so Canvas stays authoritative for pages/assignments/announcements.
Also protects mid-extraction rows (wiping an enqueue marker causes duplicate
billed LlamaParse submissions). Lookup fails **closed** — skip the chunk rather
than upsert blind.

Verified end to end:

```
BEFORE SYNC:  20 docs, avg 14,183 chars, 20 with real text
canvas-ingest: rows_upserted 526 · extracted_preserved 20 · no error
AFTER SYNC:   20 docs, avg 14,183 chars, 20 with real text, markers intact
```

That exact sequence used to destroy all 20.

## Also fixed on 08-13

**Resource drain — poller idle guard (`3f948b6`, migration applied).**
24h of `cron.job_run_details`:

```
llamaparse-poller-2m   688 runs  66 failed   86% of ALL scheduled runs
drive-content-15m       96 runs   9 failed   12%
everything else         14 runs   0 failed    2%
```

The queue was empty for effectively all 688. The 30s→2m change cut the count 4x
but not the shape: cost scaled with the clock, not the work. The 66 `job startup
timeout` failures were pg_cron running out of worker slots — which is also why
`drive-content-15m` was dropping runs. The tick now checks for pending work
before paying for an edge invocation. Idle ticks are an index lookup.

**Per-course extraction (`3f948b6`).** `canvas-file-extract` ordered
oldest-first across all courses; a `course_id` filter meant spending 27 parses
instead of 128.

**Learner-signal capture (`87bc9a0`, `d491dd4`).** Two real defects, neither
sufficient on its own:
- Bare `void promise()` after the response is dropped when the Edge isolate
  tears down. Fixed via `runInBackground` / `EdgeRuntime.waitUntil`
  (`_shared/edge-background.ts`). Applies to `persistTurn` too.
- `conceptsCoveredBy` keyed on `source_id`, but COVERS never attaches to a
  Chunk — and Lane A (chunks) is exactly the lane that carries a turn when
  concept resolution fails. Now resolves `parent_id || source_id`.

## Gotchas

- `supabase functions logs` does not exist in this CLI. Dashboard only.
  `supabase db query --linked` **does** work and bypasses RLS.
- `learner_signals` has RLS `for select to authenticated using (false)` — it is
  server-only by design. An empty browser query is not evidence.
- `brain-pipeline-v4` times out at `limit:30` (150s edge cap). Use `limit:3`.
- `canvas-file-extract` caps at 20 files per run.
- `CRON_SECRET` is in Supabase Vault as `rumbo_cron_secret`; read it via
  `public._rumbo_cron_config()`.
- Neo4j Aura Free auto-deletes; the graph is rebuildable from Postgres via
  `brain-pipeline-v4`.
